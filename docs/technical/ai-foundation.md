# AI foundation and MCP connection

PhysiCore exposes a versioned action catalog for saved project work. A compatible MCP host can discover and call the same actions through the stdio adapter or the opt-in remote transport. The first release covers project inspection, project-owned rotor-source listing and metadata inspection, selected draft edits, revisions, studies, comparison, exact result export and hosted job actions. Discover current availability in the workbench or catalog. Geometry, source authoring, additional input groups and application development are future adapters. The workbench includes a Groq chat using these same actions. External MCP clients provide their own model connection.

## Connect

1. Start an authenticated PhysiCore workspace and open a saved project. Public demo mode does not issue AI credentials.
2. In **AI client access and action review**, name the connection and choose its lifetime. The default permits reads and proposals. Enable reviewed changes and studies only when needed. Create the connection and copy the credential once.
3. Store the credential in a private file owned by the current user with permissions `600` on POSIX systems, or use a protected environment variable. Never commit it or share it in conversation. The credential is distinct from the workspace login and is limited to one project, parent authority, expiry and call count. Revoke it in the workbench when finished.
4. Install the application with its optional MCP extra (`physimesh-drone[mcp]`), or use the repository's `requirements-mcp.lock` with hash verification in the intended environment. Configure the MCP host to run `python -m physimesh.agent.mcp`, with `PHYSICORE_API_URL` set to the authenticated application origin and `PHYSICORE_AGENT_TOKEN_FILE` set to the private file. The workbench can download a configuration template without the credential. Alternatively supply `PHYSICORE_AGENT_TOKEN` through the host's protected environment. File permission checks require POSIX; use protected environment storage on other systems.

The adapter accepts HTTPS origins or loopback HTTP, rejects redirects and does not accept arbitrary file paths or URLs from model calls. It speaks stdio locally. The separate opt-in hosted MCP transport is described below. The MCP host and its model provider are separate products and may have their own configuration and costs.

## Review and results

The client discovers tools and prepares an action. A project user reviews the exact change or operation in the workbench and approves or rejects it. A client cannot approve its own request. For retries reuse the same request ID and identical arguments; a completed call returns its recorded receipt. A change is applied only to the matching saved draft version, and undo is available only while the applied version is still current. Save or discard other unsaved browser edits before applying.

Receipts record what the system actually did. If an operation was interrupted after admission, its outcome may be **uncertain**; inspect retained studies or job history before deciding what to do next. Hosted jobs report their recorded state rather than an estimated completion time. Exact exports remain subject to project permissions. Credential and parent-session authority are checked on each call.

This interface does not certify a simulation or aircraft. Existing scientific evidence and qualified human review requirements still apply.

## Groq chat

Configure a Groq key and model in **AI settings**, then open an authenticated saved project over HTTPS or loopback and send a message in **Ask PhysiCore**. The server must first be configured with an independent encryption secret; see [AI settings](ai-settings.md) for setup, access scope and key recovery. The key is saved encrypted and is not returned to the browser. Prompts and relevant action results are sent to Groq and usage may be charged by Groq. Do not enter the key into the conversation itself.

The assistant can use only currently available actions and current project permissions. Save or discard unsaved edits before approving changes. The workbench shows the proposed values and exact review details; approve or reject, then select Continue. The actual receipt is retained independently of the model's explanation. Stop requests prevent subsequent tool calls after a current provider call or action returns; that in-flight work may complete.

Conversation state is held in the browser as a signed, project-bound token, expires after 15 minutes and is lost on reload. A server restart invalidates it. The signing key and stop coordination are process-local; this implementation has not been qualified for multi-worker or load-balanced hosting. Provider requests have a 15-second socket timeout and the coordinator checks a 60-second deadline between steps, not a guarantee that an in-flight operation stops at that exact time. A live Groq session answered and inspected synthetic data, but the follow-up hit a usage limit; the saved-key flow and full live change-to-study journey remain unverified.

## Remote MCP and organization sign-in (local implementation)

The remote endpoint is opt-in and requires hosted mode, the pinned MCP extra and an explicitly configured HTTPS origin. Configure `PHYSIMESH_REMOTE_MCP_ORIGIN`, `PHYSIMESH_REMOTE_MCP_ISSUER` and `PHYSIMESH_REMOTE_MCP_JWKS_URL`. The resource URL is the origin plus `/mcp/`. It publishes protected-resource discovery at `/.well-known/oauth-protected-resource/mcp/`. The external authorization server must issue signed JWT access tokens with `typ` `at+jwt`, the MCP resource as their sole audience and a verified `client_id` claim. Only an already-provisioned active user with matching issuer and subject can use the endpoint.

Configure `PHYSIMESH_HOSTED_SIGNIN_ORIGIN`, `PHYSIMESH_HOSTED_SIGNIN_ISSUER`, `PHYSIMESH_HOSTED_SIGNIN_DISCOVERY_URL` and `PHYSIMESH_HOSTED_SIGNIN_CLIENT_ID` to enable the workbench's organization sign-in. For this integration the sign-in and remote endpoint share an origin and issuer. Register the exact callback `<origin>/api/oidc/callback` with the provider and provision the issuer/subject and project memberships through a trusted administrator. The app does not link accounts by email or provision them automatically. Provider metadata must advertise authorization code and PKCE S256 and use HTTPS authorization, token and JWKS endpoints on the configured issuer's origin. The workbench client is public and does not use a client secret.

After sign-in, open a project and grant the specific provider-issued remote client ID access under **Remote MCP connections**. A connection is scoped to one project and its selected groups, bounded by the browser session and at most 24 hours; sign-out, revocation, expiry or membership removal removes access. The human must review consequential actions in the workbench. Client IDs and supported OAuth flows depend on the identity provider and AI host. The implementation has not been verified with a real provider or Claude/ChatGPT, and does not make every application workflow available.

The public edge must terminate HTTPS and forward the original scheme and host only through explicitly trusted proxy configuration. Configure the edge and all access/trace logs to omit query strings and authorization headers, particularly on `/api/oidc/callback`; the application removes the callback query from its ASGI scope before its own access response, but cannot control upstream logs. Do not enable verbose ASGI scope or request-body logging. Review provider configuration, networking, operational security and data protection before deployment. PostgreSQL, multi-worker deployment, real-provider interoperability and security assessment remain unverified; this is not a production certification.
