# Groq workbench chat: first AI-native expansion

Status: written design approved 27 October 2026. This is the first stage of the owner's broader request for complete project action coverage, a remotely accessible MCP server and in-app conversation. The existing local MCP foundation is implemented in `codex/ai-native-foundation`.

## Outcome and scope

A user opens a saved project, enters a Groq API key and a tool-capable model ID in the workbench, then asks in plain language to inspect the saved project, propose supported edits or use existing revisions and studies. The assistant calls the existing versioned action catalog, reports actual outcomes and pauses on an action requiring human review. The user approves or rejects the exact action using the existing trusted review interface, and the conversation can continue from the recorded result. Available actions are those already implemented and authorized for the selected user and project; missing geometry, source, other authoring, report and collaboration adapters are explicitly unavailable rather than simulated.

Two approaches considered: direct model-specific handlers duplicate domain policy and drift from MCP; a provider-neutral orchestrator using the shared action gateway gives chat and MCP one source of action truth. Use the latter, with one Groq adapter initially. Future providers implement the same narrow adapter. A remote MCP transport is a later stage: it must use the same catalog and policy and standards-based authentication, and must be tested against actual client capabilities before any compatibility claim. Application source changes remain a separate owner-only capability, outside a project chat grant.

## Flow and authority

- The chat is available only within an authenticated workspace and selected saved project. Public demo mode and delegated MCP credentials cannot use the chat endpoint. Hosted users' existing project permissions govern every action.
- The user enters a key into a password field and explicitly selects or types a Groq model ID. Keep the key in browser memory for the page session only; submit it over the authenticated same-origin request to the application for the current run. Do not place it in storage, URLs, logs, error messages, receipts, downloadable files or model prompts. Clear it on project switch, logout, page close or explicit clear. Server code retains it only while handling the request. Require secure HTTPS or loopback for entering a key; never transmit one over a public plain HTTP origin.
- Explain before first send that the prompt, selected context and tool results are sent to Groq and that usage can incur the user's provider charges. Sending a message is the explicit provider-use action. No automatic provider calls occur on page load. Do not ask the user to paste a key into this conversation.
- The server accepts bounded conversation messages and the selected project, obtains the allowed catalog through the existing policy, and presents schemas to Groq. It routes validated model tool calls directly through `AgentService.call` with the trusted user's scoped context and original permissions. It never provides approval, grant management, arbitrary shell, paths, network access or code modification as model tools. Bind any project identifier to the selected project, preventing model-selected cross-project access.
- Each run is bounded to at most 8 provider requests and 12 tool calls, a 60-second overall deadline, bounded input/output and per-provider timeout. Disable parallel tool calls to preserve ordering. If a limit, model error, malformed tool call, permission change, quota or provider failure occurs, stop and show a concise error and recorded actions; never claim success. No automatic retry of uncertain side effects. Output is rendered as text, never executable HTML.
- On `awaiting_review`, stop the model loop and display the actual review and exact preview from the existing gateway. A trusted user approves or rejects through existing same-origin review controls. The action is executed by the existing confirmation flow, and an explicit Continue sends the actual outcome to Groq. Recheck current project, draft state, identity, expiry and permissions before every action and continuation. Request IDs and receipts retain existing replay protection. Preserve unsaved browser edits; disable consequential actions when the browser draft is dirty.
- Conversation messages and run state live in browser memory only, with explicit clear. No chat history or provider key is persisted by this slice. Existing action records remain durable according to current policy. Project changes, logout and new runs invalidate old responses; failed or cancelled runs do not silently continue. A page refresh loses the conversation but not a pending review or action receipt.

## Interface and tests

A dedicated workbench conversation section sits near the existing AI connection/review controls. It shows the active project, provider key and model controls, conversation, user prompt, working status, action results and pending review with a clear way to continue or stop. It follows the existing workbench design language, remains usable on phone and enlarged text, and does not present unsupported actions as available. Existing manual editors and MCP connections remain usable. All new controls require actual browser interaction checks and the owner's full interface-law recheck.

Use a simulated Groq HTTP service in tests, with no network or paid calls. Cover successful read and proposal-to-human-review-to-continuation, rejected/stale review, cross-project and viewer denial, dirty drafts, unknown/malformed tools, provider failure, limits, duplicate requests, secrets redaction, logout/project switches and late responses. Retain current action, project and MCP regression checks, plus browser verification of key clearing and responsive layout. A real Groq connection and model behavior are unverified until the user configures a key and initiates usage. Passing software tests is not scientific validation.

## Next stages

After this chat slice: add the rest of the project's action adapters with provenance, existing permissions and explicit review; implement remote MCP with appropriate identity, consent and client interoperability tests; add additional model adapters; then address isolated owner-only application development. Publication, deployment, provider spending by the developer, changes to science and physical acceptance are not implied.
