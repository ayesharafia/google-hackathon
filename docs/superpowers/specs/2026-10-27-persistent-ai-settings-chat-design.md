# Persistent AI settings and project chat

Status: Owner approved the design in conversation on 27 October 2026; written design review pending. This replaces the session-only credential choice in the earlier Groq chat design for this slice. It does not approve publication or deployment.

## Outcome and boundaries

An authenticated person configures their Groq key and model once in AI settings, then opens a saved project and uses a dedicated conversation to ask questions and request supported actions. The assistant uses the existing action catalog and project policy, shows activity and results, and pauses for a human decision on consequential actions. It does not promise actions the catalog does not support, run arbitrary code, grant itself approvals, or confer scientific or aircraft acceptance. Groq is the only provider in this slice. The provider boundary is designed to admit future adapters without claiming they already work.

Hosted settings belong to the authenticated user, not the project or organization; one person cannot use or retrieve another's key. Existing local mode has one shared workspace identity: its settings are explicitly labeled shared, and anyone with that workspace's trusted access can use the configured provider allowance. Public-access mode and delegated MCP grants cannot configure or use saved provider keys. Multi-user isolation requires hosted sign-in and its existing project permissions.

## Secret storage and configuration

Add a dedicated provider-settings store keyed by authenticated actor and provider. Store a versioned authenticated-encryption ciphertext and model metadata, with associated data binding the ciphertext to its actor and provider. Use the already locked `cryptography` dependency and a separately configured, high-entropy server encryption key; never derive it from the workspace access token. Require the same server key across instances and restarts. Server configuration documentation specifies generation, secret-manager placement, backup and loss: losing or changing the key without a migration makes existing credentials unusable, requiring re-entry. The first version does not silently rotate encryption keys.

With no valid encryption key configured, saved-provider settings fail closed with actionable setup guidance; no plaintext fallback or ephemeral replacement is created. Require HTTPS or loopback for settings and chat. Apply existing trusted-session, same-origin mutation and project authorization checks; refresh authorization before actions and reject stale sessions. Inputs, logs, validation failures, error responses, tests, database records, continuation tokens, action receipts, exports, URLs and model prompts must not expose plaintext credentials. Store only ciphertext, provider, model and timestamps; GET returns configured status and model, never the key or a reversible representation. New key input replaces the stored value atomically; blank input leaves an existing key unchanged. Delete removes the stored credential and clears its use for new requests; an already in-flight provider call may finish. No provider call occurs just from saving or loading settings.

Use bounded inputs and model ID validation, no-store responses, and portable SQLite/PostgreSQL migrations. Bind the hosted key to the stable user identity rather than a browser session; explicitly manage local shared-identity behavior without relying on a session token as encryption material. Server-side plaintext exists only for the provider request. No accidental migration of the previously pasted credential is permitted.

## Chat flow

Move provider setup out of the message composer into a clearly labeled AI settings surface with configured, missing, unavailable and replace/remove states. The project chat shows the selected project, messages, running status, actual tool activity, a message composer, stop control and review cards with before/after values. The user can switch to settings without losing an active run. Conversations remain page-session scoped in this first slice: a refresh clears transcript and model continuation, while existing action receipts and pending reviews remain governed by the current system. Communicate that limit rather than imply a saved chat history.

Sending resolves the current actor's saved provider key and model server-side. The browser no longer sends the provider key with each message. Send the prompt, applicable project context and tool results to Groq only when the user sends or explicitly continues a reviewed run, with a visible disclosure that provider usage may incur charges. Review cards use the existing trusted confirmation endpoints; no automatic approval or retry of uncertain writes. Reject or approve, show the recorded outcome, then let the user continue the conversation. Stop prevents new tool calls but cannot undo one already in flight. The existing run limits, selected-project binding, dirty-draft behavior, replay protection, cancellation and stale-response guards remain.

Provider failures, quota limits, invalid configuration, interrupted runs, changed permissions and stale reviews receive useful non-secret messages; no failed request is described as successful. Clearly distinguish unsupported actions from performed actions. Language-model responses are untrusted and can still be wrong; a prompt constraint is not an enforcement mechanism. The action gateway, not the model, decides what can run. No automatic physical validation is inferred.

## Delivery and verification

Exercise encrypted storage across restart with a stable secret; cross-user and cross-project authorization, shared local mode, public and delegated denial, missing/wrong encryption keys, replacement/removal, malformed inputs, tamper detection, redaction and no key in API responses/receipts/logs. Test a simulated provider for read, proposal, explicit review, continuation, failure and cancellation. Verify project and identity switches, concurrent runs, old responses, dirty drafts, settings updates and logout. Test both supported databases where available and document any untested production configuration.

Use a disposable local workspace and browser to check setup, refresh, model/key persistence, chat, review, keyboard navigation and responsive layout, with fake provider credentials. Perform the full interface-law review and fix actual issues. A real Groq check requires the owner to enter a replacement key privately and send a message; it may incur usage and can be blocked by provider limits. Evidence must distinguish simulated integration, live model behavior, remaining action coverage and physical validation. No deployment, main-branch publication, provider purchase, change of physics, or deletion of branches is authorized by this design.
