# Groq Workbench Chat Implementation Plan

> For agentic workers: use executing-plans inline under the repository's one-implementer rule.

**Goal:** A project user can use Groq chat to inspect saved designs and request existing reviewed actions.

**Architecture:** A bounded, provider-independent run coordinator offers the permitted action catalog to a Groq HTTP adapter. Server-owned ephemeral run state binds continuation to the actual review and current identity. The browser holds the provider key only in page memory and uses existing human review endpoints.

**Tech stack:** Python/FastAPI, Pydantic, existing action service, native browser JavaScript and disposable browser tests.

**Spec:** `docs/superpowers/specs/2026-10-27-groq-workbench-chat-design.md`.

## Constraints

No paid calls in verification, key persistence, public-demo access, delegated chat credentials, unreviewed mutation, cross-project action, science changes, publication or deployment. Limit each run to eight provider calls, twelve tool calls and 60 seconds. No parallel tools. Preserve dirty draft and reject stale context.

## Steps

1. Add fixture-driven tests for scoped action execution, review pause/continuation, provider failures, limits and authorization; run as a failing test. Implement server-owned bounded state and Groq adapter with sanitized failures, secure-origin checks and no credential persistence.
2. Add workbench chat with key/model, prompt, action results, exact review and explicit continuation. Wire context invalidation, dirty state and real review actions. Test with an injected fake provider and actual browser interactions.
3. Run focused and affected regressions, inspect desktop/phone/enlarged UI, recheck owner design law, document actual behavior/limits, persist task evidence and commit locally.
